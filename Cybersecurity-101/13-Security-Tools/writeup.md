# Security Tools & Concepts

---

## Overview

This chapter covers four core areas of defensive security technology — SIEM, Firewalls, Intrusion Detection Systems, and Vulnerability Scanning. The sections follow TryHackMe's room order for this chapter. It is worth noting that in a real security environment, these tools layer from the outside in: the firewall sits at the perimeter, the IDS monitors what passes through it, and the SIEM collects and correlates everything — with vulnerability scanning running continuously beneath all of them.

Seeing these concepts taught in a hands-on context made the exam objectives feel far more grounded — understanding *why* each tool exists and what problem it solves is a much better foundation than memorising definitions in isolation.

## SIEM — Security Information and Event Management

### What is SIEM?

A SIEM is a centralised platform used in almost every SOC environment. It collects logs from across an organisation's network, normalises them into a consistent format, correlates events across multiple sources, and triggers real-time alerts when detection rules are satisfied. Its core purpose is to give analysts a single place to monitor, investigate, and respond to security events — rather than jumping between individual machines.

---

### Log Sources

SIEM ingests logs from two broad categories of sources:

**Host-Centric Log Sources**

Generated by events occurring on individual devices such as Windows and Linux machines, and servers.

Examples include:
- A user accessing a file
- A user attempting to authenticate
- Process execution activity
- A process adding, editing, or deleting a registry key or value
- PowerShell execution

**Network-Centric Log Sources**

Generated when hosts communicate with each other or access external resources. Devices that produce these logs include firewalls, IDS/IPS systems, and routers.

Examples include:
- SSH connections
- Files accessed via FTP
- Web traffic
- A user connecting to company resources through a VPN
- Network file sharing activity

---

### Challenges in Log Management

Before SIEM existed, managing logs across an organisation was a significant problem. These are the core challenges a SIEM is designed to solve:

| Challenge | The Problem | The Impact |
| --------- | ----------- | ---------- |
| **Numerous Log Sources** | A network generates hundreds of events per second across dozens of devices | Checking every device manually during an incident is slow and tedious |
| **No Centralisation** | Logs remain on the machines that generated them | Investigators waste time connecting to each device individually via SSH or RDP |
| **Limited Context (Silo Effect)** | Individual logs only show a small piece of the picture | Threats like lateral movement look normal on a single machine but are visible only when correlated across sources |
| **Limited Analysis** | The volume of logs is too large for humans to process manually | Analysts are likely to miss critical signals buried within thousands of routine entries |
| **Format Issues** | Every device and application produces logs in a different format | Analysts must learn multiple log formats to interpret what the data is actually saying |

---

### Core SIEM Features

**Centralised Log Collection**

SIEM pulls logs from all sources — endpoints, servers, firewalls, and more — through lightweight agents or APIs and consolidates them in one place. This eliminates the need to access each machine individually.

**Normalisation**

Raw logs from different sources look completely different from one another. A Windows event log does not resemble a Linux syslog entry. SIEM breaks each log down into structured fields — a process called **parsing** — and then converts all logs into a single consistent format. This process is called **normalisation**.

**Correlation**

Individual logs in isolation provide limited value. SIEM correlates logs across multiple sources to identify relationships between events that would be invisible when looking at any single source. This is where genuinely malicious activity becomes visible.

*Example — four events occurring within a 5-minute window:*
1. A user logs in via VPN from an IP address they have never used before
2. The same user accesses documents on a shared network drive
3. The same user executes a PowerShell script
4. The system initiates an outbound network connection to an external IP

No single event here is conclusive. Correlated together, they form the pattern of a compromised account being used to exfiltrate data.

**Real-Time Alerting**

SIEM continuously evaluates incoming log data against a library of detection rules. Many rules are included by default, and analysts build additional rules over time to address specific threats relevant to their environment. When a rule's conditions are met, an alert is triggered and the analyst is notified to investigate.

**Dashboards and Reporting**

Dashboards are the primary interface analysts use to work within a SIEM. They present normalised, ingested data as actionable visual summaries. Common dashboard components include:

- Alert highlights
- System notifications
- Health alerts
- Failed login attempt lists
- Events ingested count
- Rules triggered
- Top domains visited

## Firewall

### What is a Firewall?

A firewall is a security control that monitors and filters network traffic based on defined rules, acting as a barrier between an internal network and external or untrusted networks. There are four primary types, each operating at different layers of the network stack and offering different levels of inspection capability.

---

### Firewall Types

**1. Stateless Firewall**

Operates at Layer 3 (Network) and Layer 4 (Transport). Filters each packet individually against static rules based on IP address and port number. It has no memory of previous packets — if the same source sends 100 packets, the firewall evaluates the rules 100 times independently.

- Basic allow/deny filtering
- No connection tracking
- Very high performance — suited to high-speed networks

**2. Stateful Firewall**

Operates at Layer 3 and Layer 4. Maintains a **state table** that tracks active connections. Once the first packet of a connection is permitted, subsequent packets belonging to that same session are automatically allowed without re-evaluation.

- Recognises and tracks legitimate traffic flows
- Remembers decisions made about a session
- More sophisticated rule logic than stateless firewalls

**3. Proxy Firewall (Application-Level Gateway)**

Operates at Layer 7 (Application). Acts as a complete intermediary between the internal user and the external server — the two sides never communicate directly. Inspects the actual content (payload) of traffic, not just the headers.

- Deep content inspection — looks inside packet data
- Masks internal IP addresses from the public internet
- Can filter by web category, keyword, or file type
- Capable of SSL/TLS decryption and inspection

**4. Next-Generation Firewall (NGFW)**

Operates across Layers 3 through 7. Combines traditional firewall features with an integrated security stack including Intrusion Prevention Systems (IPS) and real-time threat intelligence feeds.

- Advanced threat protection across all network layers
- Integrated IPS — actively blocks malicious traffic in real time
- **Heuristic analysis** — identifies suspicious behaviour patterns from unknown, new attacks rather than relying solely on known signatures
- Correlates local traffic data with global threat intelligence databases

---

### Firewall Rule Components

Every firewall rule is made up of the following fields:

| Component | Description |
| --------- | ----------- |
| **Source Address** | The IP address originating the traffic |
| **Destination Address** | The IP address receiving the traffic |
| **Port** | The port number associated with the traffic |
| **Protocol** | The communication protocol being used |
| **Action** | What the firewall does when the rule matches — Allow, Deny, or Forward |
| **Direction** | Whether the rule applies to incoming or outgoing traffic |

**Action Types:**

- **Allow** — permits the traffic through
- **Deny** — blocks the traffic
- **Forward** — redirects traffic to a different network segment based on forwarding rules

---

### Firewall Rule Types

| Rule Type | Description | Example |
| --------- | ----------- | ------- |
| **Inbound Rules** | Applied to incoming traffic only | Allowing incoming HTTP traffic (port 80) to a web server |
| **Outbound Rules** | Applied to outgoing traffic only | Blocking outbound SMTP traffic (port 25) from all devices except the mail server |
| **Forward Rules** | Redirect specific traffic within the network | Forwarding incoming HTTP (port 80) traffic to a web server sitting inside the internal network |

## IDS — Intrusion Detection System

### What is an IDS?

An Intrusion Detection System is a monitoring control that operates **after the firewall** — it handles the scenario where an attacker has already bypassed the perimeter. Its role is to detect potentially malicious activity that has entered the network and raise alerts for analysts to investigate.

IDS solutions are categorised by two dimensions: how they are **deployed** and how they **detect**.

---

### Deployment Modes

**Host Intrusion Detection System (HIDS)**

Installed individually on each host. Monitors and detects threats specific to that machine, providing deep visibility into its activity. The trade-off is resource intensity and management overhead — in large networks, maintaining a HIDS on every machine is demanding.

**Network Intrusion Detection System (NIDS)**

Deployed at the network level to monitor traffic across all hosts simultaneously. Provides a centralised view of detections across the entire network rather than a single endpoint.

---

### Detection Modes

| Detection Mode | How it Works | Strength | Limitation |
| -------------- | ------------ | -------- | ---------- |
| **Signature-Based** | Matches traffic against a database of known threat fingerprints | Fast and precise for known threats | Cannot detect zero-day attacks — only recognises what it has seen before |
| **Anomaly-Based** | Establishes a baseline of normal behaviour and alerts on deviations | Can detect new, unknown attacks | Prone to false positives — legitimate but unusual activity can trigger alerts |
| **Hybrid** | Combines both signature and anomaly detection | Best of both approaches — catches known and unknown threats | More complex to configure and tune |

> **Example tool — Snort:** Snort is a widely used open-source IDS that operates on signature-based detection.

---

### Snort Rule Structure

A Snort rule defines the conditions under which an alert is triggered. Each rule contains the following components:

| Component | Description |
| --------- | ----------- |
| **Action** | What to do when the rule matches (e.g. `alert`) |
| **Protocol** | The network protocol to inspect (e.g. `ICMP`, `TCP`) |
| **Source IP** | The originating IP address (`any` to match all sources) |
| **Source Port** | The originating port (`any` to match all ports) |
| **Destination IP** | The target IP — can reference a variable such as `$HOME_NET` for the local network range |
| **Destination Port** | The target port |
| **msg** | The message displayed when the rule triggers — describes the detected activity |
| **sid** | A unique Signature ID that identifies this specific rule |
| **rev** | The revision number — incremented each time the rule is modified |

## Vulnerability Scanning

### What is Vulnerability Scanning?

Vulnerability scanning is the process of systematically examining systems, networks, and applications to identify security weaknesses before an attacker can exploit them. Scans are categorised by two dimensions: whether credentials are provided, and where on the network the scan originates from.

---

### Authenticated vs. Unauthenticated Scans

**Authenticated Scans**

The scanner is provided valid credentials for the target system, allowing it to log in and inspect the system from the inside — examining internal configurations, registries, and installed software. This reflects the threat perspective of an attacker who has already gained access.

*Example: Providing a vulnerability scanner with administrative credentials to a database server to check for hidden software flaws.*

**Unauthenticated Scans**

The scanner receives only the target's IP address and no credentials. It probes the system as an external attacker would — testing what is visible and exploitable from the outside without any prior access.

*Example: Scanning a public-facing website to identify what vulnerabilities an anonymous internet user could find and exploit.*

---

### Internal vs. External Scans

**Internal Scans**

Conducted from inside the network perimeter — simulating an attacker who has already bypassed the firewall or is operating from within the organisation. The focus is on **lateral movement** risks: what can an attacker reach and exploit once they are already inside?

*Example: Scanning an internal file server or HR portal that is not accessible from the public internet.*

**External Scans**

Conducted from outside the network perimeter — simulating an attacker approaching from the public internet. The focus is on **initial access** risks: what weaknesses are visible to someone with no prior foothold in the organisation?

*Example: Scanning a company's public website or external-facing firewall for accidentally exposed ports or services.*

---

### CVSS Severity Levels

Discovered vulnerabilities are scored using the **Common Vulnerability Scoring System (CVSS)**, which provides a standardised severity rating to help teams prioritise remediation:

| Severity | Score Range | Description |
| -------- | ----------- | ----------- |
| **Low** | 0.0 – 3.9 | Minor flaws that are difficult to exploit. Typically addressed during regular maintenance cycles |
| **Medium** | 4.0 – 6.9 | Vulnerabilities that provide a potential attack path. Require attention but are not an immediate emergency |
| **High** | 7.0 – 8.9 | Serious risks that can enable unauthorised access or data theft. Should be patched as a priority |
| **Critical** | 9.0 – 10.0 | Severe flaws that are easy to exploit remotely and can result in full system compromise. Require immediate remediation |
